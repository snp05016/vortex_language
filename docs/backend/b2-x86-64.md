# B2. A second target: x86-64

<p class="page-intro">This chapter retargets the first native back end to a second processor family, x86-64, and uses the differences to find the boundary between what a back end must know about its target and what it can leave alone.</p>

<p class="vx-meta" markdown="1">Level: Intermediate · Reading time: about 25 minutes · Builds on: [B1. The simplest back end that works](b1-simplest-backend.md)</p>

???+ remember "Before you start, remember"

    ??? question "What is a target, in compiler terms?"

        The kind of machine and operating system the generated program is
        meant to run on. A back end is written for one target; a compiler
        that supports several targets has one back end per target, or one
        back end parameterized by a target description.

        Introduced in [6. The first machine code](../compiler/guide/stage-6-first-machine-code.md#words-for-this-stage).

    ??? question "What does the simplest back end do with every value, and why?"

        It gives every value its own stack slot and always loads before an
        operation and stores after it, rather than deciding which values
        belong in which registers. That sidesteps register allocation
        entirely: the price is slower code, not wrong code.

        Introduced in [B1. The simplest back end that works](b1-simplest-backend.md).

    ??? question "How does AArch64 read one element of a row-major array?"

        In up to three instructions: a constant row stride loaded or folded
        into an immediate, a multiply-add that finds the start of the right
        row, and a load whose own addressing mode scales the column index by
        the element size.

        Introduced in [A2. Reading and writing AArch64 assembly](a2-aarch64-assembly.md#one-element-of-a-fixed-shape-array).

    ??? question "Which registers does AAPCS64 use for the first integer arguments to a function?"

        `x0` to `x7`, in order; a ninth integer argument goes on the stack.

        Introduced in [A4. Calling conventions and ABIs](a4-calling-conventions.md).

    ??? question "What must every `f32` or `f64` operation be, under Vortex's rules?"

        Exactly one IEEE 754 operation, rounded to nearest with ties to
        even: no fused multiply-add, no reordering and no extra precision,
        regardless of what the target would do by default.

        Introduced in [6. The first machine code](../compiler/guide/stage-6-first-machine-code.md#lowering-the-first-program). Decision: [record 56](../decisions/numbers.md#d56).

    - Explain why the same intermediate representation can produce correct code for two different instruction sets, and name exactly what has to change between them.
    - Read a two-operand, register-memory x86-64 instruction and predict the AArch64 instructions that do the same work.
    - Work out where System V AMD64 places the first few integer and floating-point arguments, and contrast it with AAPCS64.
    - Recognize an ABI-level difference, not an instruction-level one, and explain why a single test machine cannot catch it.
    - Set up a three-target test matrix, macOS arm64, Linux arm64 and Linux x86-64, that a retargeted back end must pass on all three.

[B1](b1-simplest-backend.md) produces AArch64 assembly for one target: the
machine this guide has assumed since [stage 6](../compiler/guide/stage-6-first-machine-code.md).
That is enough to prove the whole path from source to a running program
works, but it proves nothing about the shape of a back end that supports
more than one target. This chapter adds a second one, x86-64, and asks a
narrow question about each piece of B1: does this change when the target
changes, or does it stay the same?

The answer sorts everything a back end does into two piles. Above the split,
nothing changes: the IR a lowering pass produces, the tests that check a
program's output, the front end that built the IR in the first place. Below
the split, almost everything changes: which registers exist and what they
are called, how many operands an instruction takes and whether one of them
can be a memory location, where a function's arguments arrive, how a stack
frame is laid out, even what a plain `char` means. Finding that split, in
code you can point to, is what retargeting teaches that writing one back end
cannot.

## Why x86-64, and why now

x86-64 is a reasonable second target for reasons that have little to do with
which processor is "better". The classic teaching material for writing back
ends by hand targets x86 first: *Computer Systems: A Programmer's
Perspective* builds its whole view of assembly on x86-64[^csapp], and Nora
Sandler's *Writing a C Compiler* compiles to x86-64 throughout, with a
chapter on register allocation that assumes it[^sandler]. Reading either
book, or most blog-length compiler tutorials, means reading x86-64 assembly.
A compiler that only ever emits AArch64 cannot be checked against that body
of work, and its writer cannot read it without translating first.

There is also a practical reason to bring x86-64 in now rather than later,
tied to this machine. Apple has said that macOS 27, the release this project
runs on, is the last to support Rosetta for Intel-only apps[^rosetta]; Rosetta
also does not run AVX-512 code[^rosetta-doc]. Locally testing x86-64 output on
this Mac is therefore a closing door, not a standing option, and it never
covered every instruction the target can use. The tests for this chapter's
x86-64 examples run on a Linux x86-64 machine instead, and the read of them
here matches, so it should not matter that this book was written on Apple
Silicon.

## The same function, two register-memory machines

Start as small as B1 does: one function, no loop, no array. [A2](a2-aarch64-assembly.md#the-smallest-complete-file)
opens with `add_ints`, an AArch64 function that adds its two arguments in one
instruction, `add w0, w0, w1`. Retargeting that exact function to x86-64
turns out to teach less than it should, because addition has an escape
hatch. Here is what Apple clang 21 writes for `int add_ints(int a, int b)`
at `-O2`, targeting `x86_64-unknown-linux-gnu`, checked locally in September
2026:

```gas
leal	(%rdi,%rsi), %eax
retq
```

`lea`, "load effective address", computes an address from a base register, an
index register and a scale, and normally feeds that address to a load or a
store. Nothing requires the result to be used as an address, so `lea` doubles
as a three-operand add that reads two registers and writes a third without
disturbing either of them[^sdm]. That is a genuine x86-64 instruction, but it
answers a question this chapter is not asking: it hides the cost of a
two-operand machine instead of showing it.

Subtraction has no such trick, because `a - b` is not `b - a`, and `lea`
computes only a sum. The x86-64 SysV counterpart of `add_ints`, written by
hand for this chapter, is `sub_ints`:

--8<-- "includes/examples/backend/b2-x86-64/sub_sysv.s.md"

Two instructions, where AArch64 needs one: `sub w0, w0, w1` computes
`w0 - w1` and leaves the result in a register that held neither operand
beforehand, a genuinely new destination. `subl %esi, %eax` cannot do that. It
computes `eax - esi` and overwrites `eax`, so whichever operand is going to
survive as the result has to be sitting in `eax` before the instruction runs.
Here that means copying `a` out of `edi`, where the calling convention put
it, and into `eax`, where the subtraction is happy to destroy it.

This is what a **register-memory, two-operand** instruction set means in
practice: most arithmetic and logical instructions take a destination and a
source, the destination is also one of the inputs, and the source may be a
register or a memory location but never an immediate memory-to-memory
operation. AArch64 is **load/store and three-operand**: arithmetic
instructions read two registers and write a third, and the only instructions
that touch memory are loads and stores. Three-operand code often needs fewer
instructions for the same arithmetic; register-memory code often needs fewer
instructions to get a value from memory into an operation, because the load
is folded into the instruction that uses the value. The next section shows
both effects on the same loop.

??? check "Why can clang turn `a + b` into one `lea`, but not `a - b` into one instruction?"

    `lea` computes `base + index`, and reads both operands without changing
    either of them, so it can put the sum somewhere new. There is no
    matching x86-64 instruction that computes `base - index` into a new
    register from an address-style operand; subtraction has to go through an
    ordinary destructive instruction, and that means an extra copy whenever
    neither operand already sits in the register that will hold the result.

## Registers by another name

Retargeting also renames the registers. AArch64 has 31 general-purpose
registers, `x0` to `x30`, each with a 32-bit view named `w0` to `w30`, plus a
zero register that reads as zero and discards writes[^aapcs64-gpr]. x86-64 has
16 general-purpose registers: the eight original x86 registers, extended to
64 bits and renamed `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `rsp`,
plus eight more, `r8` to `r15`, added when the architecture grew from 32 to 64
bits[^sdm]. Every one of them has a 32-bit view (`eax`, `r8d`, ...), and most
have 16-bit and 8-bit views inherited from decades of compatibility, which
AArch64 has no equivalent of.

One AArch64 rule carries over unchanged, and it is worth checking rather than
assuming. [A2](a2-aarch64-assembly.md#registers-by-name) explains that
writing a 32-bit `w` register zeroes the upper half of its 64-bit `x`
register. x86-64 keeps the same rule for its own 32-into-64 case: a write to
`eax` zeroes the upper 32 bits of `rax`[^sdm]. It does not extend the rule
downward. A write to `al`, the low 8 bits, or to `ax`, the low 16 bits,
leaves the rest of the register exactly as it was, which is a historical
accident of the 8- and 16-bit forms predating the 32-bit extension. A
retargeted back end that only ever emits 32- and 64-bit operations, as this
one does, never meets that exception, but it is a real trap for anyone
reading x86-64 code that uses the narrower forms.

??? check "A caller passes an `int32_t` argument in `edi`. What are the upper 32 bits of `rdi` afterward?"

    Zero. Any instruction that writes a 32-bit x86-64 register clears the
    upper 32 bits of the containing 64-bit register, the same rule
    [A2](a2-aarch64-assembly.md#registers-by-name) gives for AArch64's `w`
    and `x` registers. The two instruction sets agree here; the exception
    is x86-64's 8- and 16-bit writes, which this back end never emits.

## Folding a load into the arithmetic

A loop makes the register-memory difference concrete. Here is a dot product
of two `float` arrays, ordinary, portable C++:

--8<-- "includes/examples/backend/b2-x86-64/dotprod.cpp.md"

Compiled with `-O2`, loop unrolling and vectorization turned off to keep the
listing to one iteration's worth of work, and `-ffp-contract=off` to match
Vortex's ban on fusing a multiply and an add (record 56), the loop body
becomes this on AArch64, checked locally with Apple clang 21 on macOS 27,
September 2026:

```gas
LBB0_2:
	ldr	s1, [x0], #4
	ldr	s2, [x1], #4
	fmul	s1, s1, s2
	fadd	s0, s0, s1
	subs	x8, x8, #1
	b.ne	LBB0_2
```

And this on x86-64, from the same source file, `-target
x86_64-unknown-linux-gnu`, same flags, same session:

```gas
.LBB0_4:
	movss	(%rdi,%rcx,4), %xmm1
	mulss	(%rsi,%rcx,4), %xmm1
	addss	%xmm1, %xmm0
	incq	%rcx
	cmpq	%rcx, %rax
	jne	.LBB0_4
```

Both loops do six instructions of work, but they spend them differently.
AArch64 loads `a[i]` and `b[i]` into registers with two separate `ldr`
instructions, each using **post-index addressing**: `[x0], #4` reads at the
address in `x0` and then adds 4 to `x0`, so the pointer walk is folded into
the load instead of costing a separate `add`[^a64-ldr]. Only then does
`fmul` multiply two register operands. x86-64 spends one instruction loading
`a[i]` into `xmm1` (`movss`), but the second array is never loaded on its
own: `mulss (%rsi,%rcx,4), %xmm1` reads `b[i]` from memory and multiplies it
into `xmm1` in the same instruction, a memory operand folded into the
arithmetic. What it does not fold is the index: `rcx` is walked with a
separate `incq` and tested with a separate `cmpq`, because x86-64's
addressing modes take a base, an index and a scale, but no equivalent of
AArch64's write-back forms. Figure 1 lines the two loop bodies up.

and the difference is entirely the folded memory operand, not a difference
in what gets computed.

## The stack looks different, too

[A5](a5-stack-frames.md) covers stack frames in full; retargeting needs only
enough of it to know what to check for on x86-64. System V AMD64 requires the
stack pointer to be a multiple of 16 immediately before a `call`
instruction[^sysv-abi]. `call` itself pushes an 8-byte return address, so a
function's stack pointer is a multiple of 16 plus 8 the moment it starts
running; a prologue that pushes one 8-byte register, such as `rbp`, restores
16-byte alignment for the rest of the function[^bendersky]. AAPCS64 states
its rule the other way around: the stack pointer must be a multiple of 16 at
every public interface boundary, on entry as well as at a call, with no
special case for what a branch-with-link instruction does or does not
push[^aapcs64-sp]. A back end that hard-codes "the incoming stack pointer is
16-aligned" for both targets is wrong for x86-64 in a way that a single
AArch64-only test will never show.

Callee-saved registers differ in a way that matters directly for a
floating-point kernel. On System V AMD64, the integer registers `rbx`,
`rbp`, and `r12` to `r15` are callee-saved, and **no XMM register is
callee-saved at all**[^sysv-abi]: a value the callee wants to survive a call
must go through memory. On AAPCS64, `x19` to `x28` are callee-saved, and so
are `v8` to `v15`, though only their low 64 bits, so a plain `f64` can ride
out a call in `d8` to `d15` while a full 128-bit vector register cannot[^aapcs64-gpr].
A partial sum that a compiler is happy to leave in a register across a call
to, say, a bounds-check routine on AArch64 has to be spilled to the stack for
the identical call on x86-64. Both facts come from the calling convention,
not from the instruction set, and [A4](a4-calling-conventions.md) is where
the full argument-register tables and Apple's own deviations belong; this
chapter only needs to know that the answer is not the same question asked
twice.

??? check "A Vortex program keeps a live `f64` partial sum in a floating-point register across a call to the runtime's bounds-check routine. Which target must spill it to memory, and which one does not have to?"

    x86-64 System V must spill it: no XMM register is callee-saved, so a
    called function is free to overwrite every one of them. AArch64 does
    not have to: `d8` through `d15` are callee-saved, so the low 64 bits of
    the value can survive the call in place, and the back end may choose to
    keep it there.

## What retargeting does not touch

Look back at everything that changed in this chapter: register names and
counts, whether arithmetic reads memory directly, how many operands an
instruction takes, where arguments arrive, which registers survive a call,
what "the stack pointer is aligned" means at function entry. None of it
touched the loop in `dotprod.cpp`, its behavior, or the test that checks its
output. That split is the entire point of writing a second back end before
writing an optimizer: it forces every fact that only makes sense for one
machine out of the code that reads and understands Vortex, and into code that
is explicitly about one target. [B1](b1-simplest-backend.md)'s
macro-expansion strategy, one fixed instruction template per IR operation,
already has a natural seam here: retargeting means writing a second set of
templates, not changing which IR operations exist or what they mean.

The same split explains why `usize` was pinned at 64 bits for every v0.1
target rather than left to vary with the machine's word size (record 42):
AArch64 and x86-64 are both 64-bit architectures on every platform this
project tests, so nothing about array indexing or pointer arithmetic needs
to ask which target it is running on. Where the split falls is a design
choice, and getting it wrong in either direction has a name: baking a
target-specific fact into the machine-independent code produces the kind of
bug the next section is about, and pushing a machine-independent fact down
into a per-target template just duplicates it.

## One difference a single machine cannot see

Not every target difference lives in an instruction. Plain `char`, written
with no `signed` or `unsigned`, has an implementation-defined sign, and
clang chooses it per target rather than per source file. On x86-64 System V,
plain `char` is signed. On Apple's arm64 platform, Apple's own documentation
lists "char is signed" as a deliberate departure from the base AArch64
convention[^apple-arm64-char]; that sentence only makes sense if the base
convention is unsigned, and checking clang's predefined macros for a plain
`aarch64-unknown-linux-gnu` target confirms it: `__CHAR_UNSIGNED__` is
defined there and nowhere else, checked locally with Apple clang 21 in
September 2026.

--8<-- "includes/examples/backend/b2-x86-64/char_sign.cpp.md"

This example is checked on macOS arm64 and Linux x86-64, where it agrees,
and skipped on Linux arm64, where the source's own comment says it would
disagree, because one file cannot carry two different expected outputs for
one target. That is not a limitation of this book's test runner in
particular; it is the shape of the problem. A test that only runs on macOS
arm64 and Linux x86-64 would pass forever, agreeing with itself twice, while
a real difference sat one platform away, undetected. This is exactly why
[the recommended test matrix](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
for a retargeted back end is three machines, not two: macOS arm64, Linux
arm64 and Linux x86-64 cover two instruction sets, two object-file formats
and three distinct platform conventions, and GitHub's own free, standard
runners for public repositories include arm64 Linux images
(`ubuntu-24.04-arm` and newer) alongside arm64 macOS and x64 Linux, so the
third leg costs nothing to add[^gh-runners]. A CI job for each, running the
identical behavioral test, looks roughly like this:

```yaml
strategy:
  matrix:
    include:
      - { os: macos-14,          target: macos-arm64  }
      - { os: ubuntu-24.04-arm,  target: linux-arm64   }
      - { os: ubuntu-24.04,      target: linux-x86_64  }
```

That sketch is illustrative, not a file in this repository; wiring it into
this project's actual workflow is part of the exercise below, not something
this chapter does for you.

??? check "Why does a bug tied to plain `char`'s default sign slip past a test that only runs on macOS arm64 and Linux x86-64?"

    Because those two platforms happen to agree: both make plain `char`
    signed. A test suite that only ever runs on one arm64 machine and one
    x86-64 machine will pass even if the code silently assumes `char` is
    always signed. Only the Linux arm64 runner, where the default is
    unsigned, disagrees, and only running on all three catches the
    assumption.

## For Vortex

!!! vortex "Exercise"

    **Retarget your back end to x86-64 SysV, and prove it with three
    runners.** Take whichever back end you built for [B1](b1-simplest-backend.md)
    and give it a second assembly-emitting path for x86-64, following the
    System V AMD64 ABI. Keep [B1](b1-simplest-backend.md)'s strategy: every
    value in its own stack slot, one fixed instruction template per IR
    operation, no register allocation yet. Retarget the [stage 6](../compiler/guide/stage-6-first-machine-code.md#what-this-stage-is-for)
    milestone program first (`main`, literals, arithmetic, variables,
    `return`, the call to `print`), then the [stage 10](../compiler/guide/stage-10-matrix-multiplication.md#the-program-the-milestone-asks-for)
    kernel, whose signature already passes its output through a `&mut`
    parameter rather than a return value.

    Write down, in your own architecture notes rather than in code comments,
    every fact your x86-64 path needed that the AArch64 path did not:
    register names and the argument registers you chose to use, which
    registers you treat as callee-saved, how you compute a stack frame's
    size and alignment, and what your assembler directives and symbol names
    look like on Linux (no leading underscore, unlike Apple's Mach-O). Then
    set up a build matrix with three jobs, macOS arm64, Linux arm64 and
    Linux x86-64, each running the same behavioral test: compile a Vortex
    program, run it, and check its output and exit status, exactly as
    [B1](b1-simplest-backend.md)'s differential testing already does for
    one target.

    **Not yet.** Do not write a register allocator; every value still lives
    in memory ([C3](c3-linear-scan.md) and [C4](c4-graph-coloring.md)
    build one). Do not write your own assembler or object-file writer for
    either target; the system assembler and linker still finish the job
    ([B3](b3-object-files.md)). Do not retarget floating-point and vector
    code beyond scalar arithmetic; lanes and lengths belong to
    [A3](a3-floats-and-vectors.md). Do not try to make the x86-64 path fast;
    matching [B1](b1-simplest-backend.md)'s AArch64 path for correctness,
    at whatever instruction count that takes, is the whole goal here.

    **Done when** your unmodified compiler passes the same behavioral test
    on all three platforms in your matrix, and fails on at least one of them
    when you deliberately reintroduce a single AArch64-only assumption, such
    as hard-coding eight integer argument registers, allowing fused
    multiply-add, or assuming the incoming stack pointer needs no
    adjustment for x86-64's return-address push. A retargeted back end that
    has never been shown to fail on a target-specific bug has not shown that
    it can catch one.

## Key ideas

!!! recap "You can now answer"

    - **Why can the same IR feed two different back ends without changing?** Because target-specific facts, registers, encodings, calling conventions, addressing modes, live entirely below the point where IR is lowered to machine code; nothing above that point needs to know which target it is.
    - **What must a two-operand machine do that a three-operand machine does not, to compute `a - b`?** Copy one operand into the register that will hold the result, because a destructive instruction overwrites one of its own inputs.
    - **Where do the first six integer arguments go under System V AMD64?** `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`, in order; a seventh goes on the stack. AAPCS64 uses eight registers, `x0` to `x7`, for the same purpose.
    - **Which x86-64 registers can hold a floating-point value across a call safely?** None: System V AMD64 has no callee-saved XMM register, unlike AArch64's `d8` to `d15`.
    - **Why do macOS arm64 and Linux x86-64 agree on plain `char`'s sign while Linux arm64 disagrees?** Apple's arm64 platform deliberately overrides the AArch64-family default (unsigned) to match the x86 convention (signed); a plain Linux arm64 target keeps the family default.
    - **Why is one test machine not enough to trust a retargeted back end?** Some correctness facts are ABI-level, not instruction-level, and differ between platforms that share an instruction set; only running on every platform in the matrix exposes them.
