# B2. A second target: x86-64

<p class="page-intro">This chapter retargets B1's back end to a second processor family, x86-64 on Linux, and uses every difference it meets to find the line between what a back end must know about its target and what it can leave alone. Drawing that line now, before an optimizer exists, keeps AArch64 facts out of the parts of Vortex that should never know them.</p>

<p class="vx-meta" markdown="1">Level: Intermediate · Reading time: about 40 minutes · Builds on: [B1. The simplest back end that works](b1-simplest-backend.md), [A4. Calling conventions and ABIs](a4-calling-conventions.md)</p>

???+ remember "Before you start, remember"

    ??? question "What is a target, in compiler terms?"

        The kind of machine and operating system the generated program is
        meant to run on. Two targets can share an instruction set and still
        differ, as Linux arm64 and macOS arm64 do.

        Introduced in [6. The first machine code](../compiler/guide/stage-6-first-machine-code.md#words-for-this-stage).

    ??? question "What does the simplest back end do with every value, and why?"

        It gives every value its own stack slot, loads operands right before
        each template and stores the result right after. No value lives in a
        register past its own template, so there is nothing to allocate.

        Introduced in [B1. The simplest back end that works](b1-simplest-backend.md).

    ??? question "What separates a register-memory architecture from a load/store one?"

        In a register-memory architecture an ordinary arithmetic instruction
        may name a memory location as an operand. In a load/store
        architecture only loads and stores touch memory, and arithmetic works
        on registers.

        Introduced in [A1. The machine model](a1-machine-model.md).

    ??? question "Which registers carry the first integer arguments on AAPCS64 and on SysV AMD64?"

        `x0` to `x7` on AAPCS64; `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` on
        SysV AMD64. The seventh integer argument goes on the stack on
        x86-64 and in a register on AArch64.

        Introduced in [A4. Calling conventions and ABIs](a4-calling-conventions.md#a-third-convention-sysv-amd64).

    ??? question "What must `MIN / -1` and `MIN % -1` do for `i32` in Vortex?"

        `MIN / -1` is an overflow runtime error, because the true quotient
        does not fit. `MIN % -1` is 0 and is not an error, because the true
        remainder fits.

        Introduced in [Operators, record 33](../decisions/operators.md#d33) and [9. Runtime safety](../compiler/guide/stage-9-runtime-safety.md#integer-division-and-remainder-by-zero).

    - Read x86-64 assembly in AT&T syntax: operand order, size suffixes and memory operands.
    - Retarget B1's templates to x86-64 and trace a stack-slot program by hand, including the frame size SysV alignment demands.
    - Explain why a divide template is target-specific on x86-64 in two ways, fixed registers and a trap, and connect the trap to Vortex's rule for `MIN % -1`.
    - Compare what each instruction set folds into an addressing mode in the same compiled loop.

[B1](b1-simplest-backend.md) produces AArch64 assembly for one target. That
proves the path from source to running program works, but it proves nothing
about which parts of that back end belong to AArch64 and which belong to
Vortex. This chapter adds a second target and asks one question of every
piece of B1: does this change when the target changes?

The answer sorts a back end into two piles. Above the line nothing changes:
the IR, the order in which templates are chosen, the tests that check a
program's output. Below it almost everything does: register names, how many
operands an instruction takes, whether one of them may be memory, where
arguments arrive, how big a frame must be, which instructions can trap, even
how a symbol is spelled. Finding that line in code you can point to is what
a second back end teaches that the first one cannot.

## Why x86-64, and why second

Much of the classic material on writing a back end by hand targets x86-64.
Nora Sandler's *Writing a C Compiler* translates C into x64 assembly and
ends with a chapter on register allocation[^sandler]; Jeremy Siek's
*Essentials of Compilation* compiles to x86-64 throughout[^siek]. A compiler
writer who reads only AArch64 has to translate every listing in those books
before learning from it.

There is also a reason to add it now rather than later, and it comes from
this machine. Apple says macOS 27, the release this project runs on, is the
final one that supports Rosetta for Intel-only apps[^rosetta], and Rosetta
has never run AVX-512 instructions[^rosetta-doc]. Rosetta also runs macOS
programs, while this chapter's target is Linux: ELF object files and the
SysV AMD64 calling convention. So this chapter's x86-64 examples are
assembled and run by the Linux x86-64 runner of the examples harness, and the
exercise asks for the same arrangement in your own CI.

Order matters too. Every chapter from [C1](c1-instruction-selection.md) on
adds code that looks at instructions: a tiler, a liveness pass, an
allocator. If that code is written against one target, AArch64 assumptions
settle into it unnoticed. Adding a second target first forces the target
interface to exist while the back end is still small.

## Reading AT&T syntax

x86-64 has two common spellings. Intel's manuals use **Intel syntax**; the
GNU assembler, clang's `-S` output on Linux and most Unix tooling default to
**AT&T syntax**. The instructions are the same; the text differs in four
ways the GNU assembler documents[^gas-att]:

- Operand order is reversed: AT&T writes the source first and the
  destination last. Intel's `add eax, 4` is AT&T's `addl $4, %eax`.
- Registers carry a `%` prefix and immediates a `$` prefix.
- The operand size is a suffix on the mnemonic: `b` for 1 byte, `w` for 2,
  `l` for 4 and `q` for 8. `movl` moves 4 bytes; `subq` subtracts 8.
- A memory operand is written `disp(base, index, scale)` and means the
  address `base + index * scale + disp`, where the scale is 1, 2, 4 or
  8[^gas-mem]. Intel writes the same address `[base + index*scale + disp]`.

A few mnemonics are renamed as well: Intel's `cdq`, which this chapter needs
for division, is `cltd` in AT&T naming[^gas-mnem]. Figure 1 takes one
instruction from a loop later in this chapter apart.

The reversed order is the one that bites. `subl %esi, %eax` computes
`eax - esi` into `eax`: read it right to left, "from `eax` take away
`esi`". The rest of this chapter uses AT&T syntax, because it is what your
Linux tools will print.

??? check "What does `movl 8(%rsp), %eax` do, and what would it look like in Intel syntax?"

    It loads the 4 bytes at address `rsp + 8` into `eax`: the `l` suffix
    gives the size, `8(%rsp)` is a memory operand with a displacement and
    a base, and `%eax`, written last, is the destination. In Intel syntax
    it is `mov eax, dword ptr [rsp + 8]`.

## One subtraction, two instruction shapes

Start as small as [A2](a2-aarch64-assembly.md#the-smallest-complete-file)
does, with a function that combines its two `int` arguments. For
`a + b`, Apple clang 21 at `-O2` with `-target x86_64-unknown-linux-gnu`
writes this (checked locally, 24 September 2026):

```gas
leal	(%rdi,%rsi), %eax
retq
```

`lea`, **load effective address**, computes the address a memory operand
names and writes that address into a register, without reading memory and
without changing the flags[^fc-lea]. Nothing requires the result to be used
as an address, so `lea` doubles as an add that reads two registers and writes
a third. That hides the shape this section wants to show. Subtraction has no
such escape, because an address is always a sum. Here is `sub_ints`, written
by hand for SysV AMD64:

--8<-- "includes/examples/backend/b2-x86-64/sub_sysv.s.md"

AArch64 needs one instruction for the same function: `sub w0, w0, w1` reads
two registers and may write a third. x86-64's `subl %esi, %eax` cannot name
a third register. It reads `eax` and `esi` and writes the difference back
into `eax`, destroying one of its inputs. An instruction like that is
**destructive**, and an instruction set whose arithmetic mostly takes this
form is a **two-operand** set: one operand is both an input and the
destination. So whichever value will become the result must be copied into
the destination register first, which is what `movl %edi, %eax` does.

x86-64 is also the register-memory machine [A1](a1-machine-model.md)
described: the source operand of `subl` may be a register, an immediate or a
memory location. At most one operand may be in memory: two memory operands
cannot appear in one instruction[^fc-sub]. AArch64 is **three-operand** and
load/store: arithmetic reads two registers and writes a third, and only
loads and stores touch memory. Three operands save copies; memory operands
save loads. The next two sections show both effects.

??? check "Why can clang turn `a + b` into one `lea`, but not `a - b`?"

    `lea` computes an address, and an x86-64 address is always a sum of a
    base, a scaled index and a displacement. That sum can be written to a
    fresh register. There is no address form that subtracts one register
    from another, so `a - b` has to go through the destructive `sub`, with
    a copy first because neither operand already sits in `eax`.

## Registers by another name

x86-64 has sixteen 64-bit general-purpose registers: the eight x86
registers widened and renamed `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`,
`rbp` and `rsp`, plus `r8` to `r15`. Every one of them also has a 32-bit, a
16-bit and an 8-bit name: `eax`, `ax` and `al` for `rax`, `r8d`, `r8w` and
`r8b` for `r8`, and so on[^ms-x64]. (Intel's APX extension adds `r16` to
`r31`; the current psABI already lists them as temporaries[^sysv-abi].
Nothing in this book uses them.) AArch64 has 31, `x0` to `x30`, each with
a 32-bit `w` name[^aapcs64]. One of the sixteen, `rsp`, is the stack
pointer, so a template set on x86-64 has fewer spare registers than one on
AArch64 before it has chosen anything.

One rule carries over. [A2](a2-aarch64-assembly.md#registers-by-name)
showed that writing a `w` register zeroes the upper half of its `x`
register. On x86-64, an instruction that writes a 32-bit register also
zero-extends into the whole 64-bit register, but one that writes an 8-bit or
16-bit register leaves the other bits as they were[^ms-x64]. A back end that
emits only 32-bit and 64-bit operations never meets that exception. A back
end that stores a `bool` with an 8-bit instruction and later reads the full
register does.

??? check "A caller loads an `i32` argument into `edi` with a 32-bit `movl`. What are the upper 32 bits of `rdi` afterward?"

    Zero. A write to a 32-bit register clears the upper 32 bits of the
    64-bit register that contains it, the same rule AArch64 has for `w`
    and `x`. Had the caller written only `di` (16 bits) or `dil` (8 bits),
    the rest of `rdi` would still hold whatever was there before.

## B1's templates, retargeted

B1 gave each IR node one fixed template. Retargeting means writing a second
template for each node, keeping everything else. Here are B1's templates and
their x86-64 counterparts, where `[s]` stands for slot `s`, at byte offset
`4*s` from the stack pointer:

| Node | AArch64 (B1) | x86-64 SysV | Instructions |
| --- | --- | --- | --- |
| `Const(v)` into `[s]` | `mov w0, #v` / `str w0, [s]` | `movl $v, [s]` | 2 and 1 |
| `Sub(l, r)` into `[s]` | `ldr w0, [l]` / `ldr w1, [r]` / `sub w0, w0, w1` / `str w0, [s]` | `movl [l], %eax` / `subl [r], %eax` / `movl %eax, [s]` | 4 and 3 |
| `Mul(l, r)` into `[s]` | as `Sub`, with `mul` | as `Sub`, with `imull` | 4 and 3 |

Two x86-64 features shorten every template. `movl` can store an immediate
straight to memory, so a constant needs no register. And the right operand
of `subl`, `addl` or `imull` can be read from its slot by the arithmetic
instruction itself; the two-operand `imull` multiplies its destination
register by a register or memory source and keeps the low 32 bits of the
product[^fc-imul]. The left operand still has to be loaded into `eax` first,
because the instruction is destructive.

The frame changes too, and not because of the templates. SysV AMD64 requires
the stack pointer to be a multiple of 16 immediately before a `call`, which
means that at a function's first instruction `rsp + 8` is the multiple of
16, because `call` has pushed an 8-byte return address[^sysv-abi]. AArch64's
`bl` pushes nothing, and AAPCS64 asks for `sp mod 16 = 0` at the function's
entry as well[^aapcs64]. [A4](a4-calling-conventions.md#a-third-convention-sysv-amd64)
showed the consequence for calls; here it sets the frame size. A frame of
`n` bytes keeps the alignment only when `n + 8` is a multiple of 16.

Here is B1's `(7 - 2) * 3` again, generated by the x86-64 templates:

--8<-- "includes/examples/backend/b2-x86-64/stack_calc_x86.s.md"

Walk it with Figure 2. On entry, `rsp` points at the return address and is 8
bytes past a 16-byte boundary. Four `i32` slots need 16 bytes, but 16 + 8 is
24, not a multiple of 16, so the frame is 24 bytes and the last 8 are
padding.

`movl $7, 0(%rsp)` and `movl $2, 4(%rsp)` fill slots 0 and 1. The
`Sub` template loads 7 into `eax`, subtracts the 2 it reads from `4(%rsp)`,
and stores 5 in slot 2. Slot 3 gets 3. The `Mul` template loads 5, multiplies
by the 3 at `12(%rsp)`, and leaves 15 in `eax`, the SysV return register.
Eleven instructions against sixteen in B1's `stack_calc.s`, and a frame 8
bytes larger. Assembled and linked into a small caller, a macOS copy of this
function (with a leading underscore and without the ELF-only directives)
returned 15 under Rosetta on this Mac, 24 September 2026.

A leaf function like this one could skip moving `rsp` at all: SysV reserves
the 128 bytes below `rsp` as a **red zone** that signal handlers must not
touch, so a function that calls nothing may keep its whole frame
there[^sysv-abi][^bendersky]. [A5](a5-stack-frames.md#the-red-zone) covers
it, including the fact that Linux arm64 has no such zone. The simplest back
end ignores it on both targets, so that a template that later grows a call
never has to move the frame.

??? note "The completed trace"

    - Step 4: `movl 4(%rsp), %eax` / `addl 8(%rsp), %eax` / `movl %eax, 12(%rsp)`, value 7.
    - Step 5: `movl 0(%rsp), %eax` / `imull 12(%rsp), %eax` / `movl %eax, 16(%rsp)`, value 14.
    - Step 6: `movl $1, 20(%rsp)`, value 1.
    - Step 7: `movl 16(%rsp), %eax` / `subl 20(%rsp), %eax` / `movl %eax, 24(%rsp)`, value 13.

    Seven slots take 28 bytes. The smallest frame of at least 28 bytes
    with `n + 8` a multiple of 16 is 40, so the prologue is
    `subq $40, %rsp`. B1's AArch64 frame for the same trace is 32 bytes.
    The x86-64 body is 13 instructions against B1's 20.

??? check "A function needs 32 bytes of slots. Which frame size keeps SysV's alignment, and which keeps AAPCS64's?"

    On SysV AMD64, 40: the frame plus the 8-byte return address must be a
    multiple of 16, and 32 + 8 = 40 is not, while 40 + 8 = 48 is. On
    AAPCS64, 32: the stack pointer is already a multiple of 16 at entry,
    so any multiple of 16 works. A back end that computes one frame size
    for both targets gets one of them wrong.

## Division: fixed registers and a trap

Addition, subtraction and multiplication retarget by swapping mnemonics.
Division does not. Here is what clang writes for `a / b` and `a % b` on
`int` at `-O2` (checked locally, 24 September 2026):

| | AArch64 | x86-64 SysV |
| --- | --- | --- |
| `a / b` | `sdiv w0, w0, w1` | `movl %edi, %eax` / `cltd` / `idivl %esi` |
| `a % b` | `sdiv w8, w0, w1` / `msub w0, w8, w1, w0` | `movl %edi, %eax` / `cltd` / `idivl %esi` / `movl %edx, %eax` |

The x86-64 column shows the first difference. `idivl` names only its
divisor. It divides the 64-bit value in `edx:eax` (the upper half in
`edx`, the lower in `eax`) and leaves the quotient in `eax` and the
remainder in `edx`[^fc-idiv]. `cltd` prepares that dividend by copying the
sign bit of `eax` into every bit of `edx`[^fc-cdq][^gas-mnem]. A divide
template on x86-64 therefore has **fixed registers**: operands that must be
in particular registers, whatever else the back end wanted to keep there.
B1's discipline hides the cost today, because nothing lives in a register
between templates. An allocator in [C3](c3-linear-scan.md) will have to
respect `eax` and `edx` around every division.

The second difference changes behavior as well as registers. `idiv` raises a
**divide error**, a processor exception, when the divisor is zero or when
the quotient does not fit in the destination, which is exactly the case
`MIN / -1`[^fc-idiv]. On Linux the process receives `SIGFPE`, whose default
action ends it abnormally[^posix-signal]. AArch64's `sdiv` traps on neither. The
next example runs it on the edge cases, with the remainder computed as clang
computes it, `a - (a / b) * b` with `msub`:

That output comes from this Mac (Apple M4 Pro, 24 September 2026), and the
harness checks the same bytes on the Linux arm64 runner: a zero divisor
gives a quotient of 0 and `MIN / -1` gives `MIN` again, with no signal.

Now put that beside [record 33](../decisions/operators.md#d33). A zero
divisor and `MIN / -1` must be runtime errors, so every back end needs
checks before the divide, and forgetting one gives a quiet wrong answer on
AArch64 and a crash on x86-64. `MIN % -1` must be 0. On AArch64 the
unguarded `sdiv` and `msub` already give 0, so a remainder template with no
special case passes every test on both arm64 runners. On x86-64 the same
template reaches `idivl` with `MIN` and `-1`, and the program dies. A C
program doing that remainder, built for x86-64 and run under Rosetta on this
Mac, was killed by `SIGFPE` (24 September 2026). Record 33 names the case
directly: `MIN % -1` gives 0 "even where a divide instruction would fault".

??? check "Your remainder template passes `print(remainder(-2147483647 - 1, -1))` on macOS arm64. Why is that not evidence it is correct?"

    Because AArch64's `sdiv` returns `MIN` for `MIN / -1` without trapping,
    and `msub` then computes `MIN - MIN * -1`, which wraps to 0: the right
    answer, reached without any check. The same template on x86-64 reaches
    `idiv` with a quotient that does not fit, which raises a divide error.
    Only a run on x86-64 shows whether the template handles the case
    itself.

## Folding a load into the arithmetic

A loop shows what each instruction set folds into its addressing modes. Here
is a dot product of two `float` arrays in portable C++:

--8<-- "includes/examples/backend/b2-x86-64/dotprod.cpp.md"

Compiled by Apple clang 21 at `-O2`, with unrolling and vectorization off to
keep one iteration per loop body and `-ffp-contract=off` to match Vortex's
ban on fusing a multiply and an add ([record 56](../decisions/numbers.md#d56)),
the AArch64 loop body is this (checked locally, 24 September 2026):

```gas
LBB0_2:
	ldr	s1, [x0], #4
	ldr	s2, [x1], #4
	fmul	s1, s1, s2
	fadd	s0, s0, s1
	subs	x8, x8, #1
	b.ne	LBB0_2
```

With `-target x86_64-unknown-linux-gnu` and the same flags:

```gas
.LBB0_4:
	movss	(%rdi,%rcx,4), %xmm1
	mulss	(%rsi,%rcx,4), %xmm1
	addss	%xmm1, %xmm0
	incq	%rcx
	cmpq	%rcx, %rax
	jne	.LBB0_4
```

Both bodies have six instructions, spent differently. AArch64 loads `a[i]`
and `b[i]` with two `ldr` instructions using **post-index addressing**:
`[x0], #4` loads from the address in `x0` and then adds 4 to `x0`, so each
pointer advances inside its own load
([A2](a2-aarch64-assembly.md#loads-stores-and-addresses))[^a64-ldr-imm].
x86-64 loads `a[i]` with `movss`, then reads `b[i]` inside the multiply:
`mulss (%rsi,%rcx,4), %xmm1` is Figure 1's instruction. What x86-64 cannot
fold is the index update. Its memory operands have a base, an index, a scale
and a displacement and nothing more[^gas-mem]: no form writes an updated
address back to a register, so `rcx` advances with a separate `incq`.

## Calls cross a different contract

[A4](a4-calling-conventions.md) holds the full register tables; retargeting
needs the rows that change a template. Integer arguments arrive in `rdi`,
`rsi`, `rdx`, `rcx`, `r8` and `r9`, floating-point ones in `xmm0` to `xmm7`,
and results come back in `rax` or `xmm0`[^sysv-abi]. B1's prologue stores
each incoming argument to its slot, so the change is a different list of
source registers, and a seventh integer argument that must be read from the
caller's stack above the return address.

Which registers survive a call changes more. SysV AMD64 preserves `rbx`,
`rbp` and `r12` to `r15`, and no XMM register at all[^sysv-abi]. AAPCS64
preserves `x19` to `x28` and the low 64 bits of `v8` to `v15`[^aapcs64].
Under B1's scheme nothing lives in a register across a call, so neither
table matters yet. It will matter the day an allocator wants to keep an
`f64` running sum in a register across a call to the runtime: AArch64 can
park it in `d8`, and x86-64 has to spill it.

One ABI detail lands in B1's templates today. When the generated code calls
a C function with a variable argument list, such as a runtime `print` built
on `printf`, SysV requires `al` to carry the number of vector registers the
call uses[^sysv-abi]. A call template for x86-64 has to set it before
every such call; AArch64 has no counterpart, so nothing in B1's AArch64
templates would remind you.

??? check "A Vortex function keeps an `f64` partial sum live across a call to the runtime's `print`. Which target forces it into memory, and which does not?"

    x86-64 SysV forces a spill: no XMM register is callee-saved, so the
    callee may overwrite all of them. AArch64 does not: the low 64 bits of
    `v8` to `v15` are callee-saved, and an `f64` is exactly 64 bits, so
    it can wait in `d8`.

## What retargeting does not touch

Look back at what changed: register names and counts, operand order in the
text, how many operands an instruction takes, whether one may be memory,
which registers a division needs, which instructions trap, the frame-size
rule, argument registers and callee-saved sets. None of it touched the IR,
the postorder walk that chose templates, the slot numbering, or the tests
that check a program's output.

That is the line this chapter was looking for, and B1's design already
follows it: templates are chosen by node kind, and the text of each template
is the only thing that names a machine. Retargeting means a second set of
templates, a second frame rule and a second ABI table, with the IR and its
meaning left alone. Where a fact belongs is a design decision. A fact about
x86-64 that leaks into code above the line, such as "division needs no check
because the hardware traps", breaks the other target. A fact about Vortex
pushed below it, such as record 33's remainder rule written separately into
each template set, gets written twice and can drift apart.

Some facts stay the same only because of choices made earlier. `usize` is 64
bits on both targets because [record 42](../decisions/numbers.md#d42)
leaves its width to the implementation and every v0.1 target chose 64. A
32-bit target would make that width a target fact too.

## Three machines, not two

Some differences are not in the instruction set at all. Plain `char` in C,
written with neither `signed` nor `unsigned`, has a sign each ABI chooses.
SysV AMD64 makes it a signed byte[^sysv-abi], AAPCS64 an unsigned
byte[^aapcs64], and Apple's arm64 platform departs from AAPCS64 and makes it
signed[^apple-arm64]. Vortex's own `char` is a 4-byte Unicode scalar value,
so this never reaches Vortex programs, but it does reach a runtime written in
C that reads bytes through plain `char`:

So the test matrix for a retargeted back end has three machines: macOS
arm64, Linux arm64 and Linux x86-64. Together they cover two instruction
sets, two object-file formats (Mach-O and ELF) and three calling
conventions (Apple arm64, AAPCS64 and SysV AMD64). GitHub's standard hosted
runners for public repositories include arm64 macOS (`macos-14` and later),
arm64 Linux (`ubuntu-24.04-arm`) and x64 Linux (`ubuntu-24.04`)[^gh-runners],
so no leg needs an emulator. In a GitHub Actions workflow the matrix looks
roughly like this:

```yaml
strategy:
  matrix:
    include:
      - { os: macos-14,         target: macos-arm64  }
      - { os: ubuntu-24.04-arm, target: linux-arm64  }
      - { os: ubuntu-24.04,     target: linux-x86_64 }
```

That sketch is not a file in this repository. This book's own examples
harness runs on the same three platforms, which is why
`stack_calc_x86.s` and `sub_sysv.s` are checked only on Linux x86-64 and
`div_edges.cpp` only on the two arm64 platforms.

??? check "Why does a bug tied to plain `char`'s sign pass on macOS arm64 and Linux x86-64?"

    Both make plain `char` signed: SysV AMD64 by its own rule and Apple
    arm64 by departing from AAPCS64. Only Linux arm64 follows AAPCS64's
    unsigned `char`, so a runtime that assumes a signed `char` fails there
    and nowhere else.

## Key ideas

!!! recap "Questions you can now answer"

    - **What changes when a back end gets a second target, and what does not?** Templates, register names, the frame-size rule and the ABI table change; the IR, template choice and the tests that check output do not.
    - **How do you read `subl %esi, %eax`?** AT&T puts the destination last: it computes `eax - esi` into `eax`, destroying the old `eax`.
    - **Why is B1's `Sub` template shorter on x86-64?** The right operand is read from memory by `subl` itself, and a constant is stored to its slot directly, but the left operand must still be copied into the destination first.
    - **Why does a 16-byte slot area need a 24-byte frame on SysV AMD64?** `call` pushed an 8-byte return address, so the frame plus 8 must be a multiple of 16.
    - **Why is division the template that differs most?** `idiv` uses fixed registers, `edx:eax` in and `eax` and `edx` out, and it traps on a zero divisor and on `MIN / -1`, where AArch64's `sdiv` returns a value.
    - **Why three runners?** Each of macOS arm64, Linux arm64 and Linux x86-64 catches a bug the other two pass: a Mach-O-only spelling, an unsigned `char`, and a divide trap.
