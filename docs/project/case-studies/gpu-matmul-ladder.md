# GPU matmul ladder

<p class="page-intro">This case study will climb a matrix-multiplication ladder on two GPUs: the Apple GPU in the owner's Mac and a rented NVIDIA GPU. Each rung adds one hardware idea, is generated by Vortex, is checked against the CPU reference and is explained by a profiler counter. Nothing has been built yet, so every result table below is empty.</p>

## The question

**Question.** Starting from a naive kernel, how far toward the vendor's
matrix-multiplication library can kernels generated by Vortex climb on an
Apple GPU and on an NVIDIA GPU, and can each step be explained by a measured
hardware counter?

**Claim.** None yet. When the tables are full, the claim will have this shape:
"On GPU *G*, kernels generated by Vortex climb from *a*% to *b*% of the vendor
library over *n* rungs, with results identical to the CPU reference, and each
rung's gain is explained by the counter shown next to it."

A **kernel** is a function that runs on the GPU, executed by many threads at
once. A **ladder** is a sequence of kernels that compute the same product,
each adding one change to the one before; each step is a **rung**. The
**vendor library** is the GPU maker's own tuned matrix multiplication: cuBLAS
on NVIDIA,[^cublas] and the Metal Performance Shaders matrix multiplication on
Apple.[^mps]

## Why employers care

In the compiler and performance job postings read while planning these pages
(September 2026), GPU and accelerator kernel programming was a frequent ask.
The programming model named most often was CUDA, together with NVIDIA's
profilers; Metal almost never appeared. The performance-heavy roles asked for
more than a fast kernel: absolute numbers, a fraction of a derived peak, a
comparison with the vendor library, and an explanation of the gap that
remains. A ladder with profiler evidence at every rung is that evidence in a
form a reviewer can read in minutes.

Each track has its reason. The NVIDIA track maps to far more postings. The
Apple track runs on the owner's own machine every day, so ideas get tried and
measured quickly, without paying for time on a rented machine.

## What to build

The study needs four things first:

- the CPU reference, which is v0.1's naive matrix multiplication
  ([stage 10](../../compiler/guide/stage-10-matrix-multiplication.md));
- a written decision on what Vortex emits for each GPU. Chapter
  [M12](../../mlir/m12-vortex-gpu-path.md) lays out the options (Metal
  Shading Language source, PTX through LLVM's NVPTX back end, MLIR's `gpu`
  dialect, or a mix) without choosing, and the choice goes in a
  [decision record](../../decisions/index.md);
- the toolchains described below, on the machines that need them;
- the [benchmark harness](benchmark-harness.md) (A2), extended to time GPU
  work.

| | Apple track | NVIDIA track |
| --- | --- | --- |
| Machine | The owner's Mac, with the M4 Pro's GPU | A rented Linux machine with one NVIDIA GPU |
| What Vortex emits | Metal Shading Language (MSL) source, compiled while the program runs with `makeLibrary(source:options:)`[^makelibrary] | PTX through an LLVM built with the NVPTX target,[^nvptx] or CUDA C++ |
| Vendor library | MPS matrix multiplication[^mps] | cuBLAS[^cublas] |
| Profiler | Xcode's Metal debugger and GPU counters[^apple-gpu][^gpu-counters] | Nsight Compute[^ncu] |

These routes follow from what the owner's machine had on 2026-09-23. The
offline `metal` compiler was not installed (it needs Xcode's separate Metal
Toolchain component), so compiling MSL source at run time is the route that
works today. The local LLVM 18.1.8 build registers only AArch64 targets, so
PTX needs an LLVM built with the NVPTX target. And NVIDIA's CUDA toolkit
dropped macOS after version 10.2,[^cuda102] so NVIDIA work happens on the
rented machine. Nsight Compute's user interface runs on macOS on Apple
silicon,[^ncu-notes] so reports collected on the rented machine can be read
on the Mac.

The rungs follow the order of a published CUDA worklog by Simon
Boehm[^boehm] and the tile hierarchy in NVIDIA's CUTLASS
documentation.[^cutlass] Chapter [G10](../../gpu/g10-matmul-ladder.md)
explains each one.

| Rung | Change | The hardware idea it tests | Taught in |
| --- | --- | --- | --- |
| 1 | Naive: one thread per element of C | Baseline: every operand comes from device memory | [G2](../../gpu/g2-simt.md), [G10](../../gpu/g10-matmul-ladder.md) |
| 2 | Coalesced loads | Neighbouring threads should read neighbouring addresses | [G4](../../gpu/g4-memory-performance.md) |
| 3 | Tiles in shared memory (threadgroup memory on Apple) | Data reused from on-chip memory saves device-memory reads | [G3](../../gpu/g3-memory-hierarchy.md) |
| 4 | Several outputs per thread in one direction | A value loaded into a register can be reused several times | [G5](../../gpu/g5-occupancy.md), [G10](../../gpu/g10-matmul-ladder.md) |
| 5 | A small two-dimensional block of outputs per thread | An outer product in registers raises the arithmetic done per load | [G10](../../gpu/g10-matmul-ladder.md) |
| 6 | Vector loads | Wider loads move the same data in fewer instructions | [G4](../../gpu/g4-memory-performance.md) |
| 7 | Bank-conflict avoidance | Shared memory is split into banks, and threads that hit the same bank wait for each other | [G4](../../gpu/g4-memory-performance.md) |
| 8 | Tuned tile sizes | The best sizes depend on the GPU; chosen by the tuner of case study [A9](cost-model-autotuner.md) | [G5](../../gpu/g5-occupancy.md), [P15](../../optimize/p15-choosing-parameters.md) |
| 9 | Warp tiling (SIMD-group tiling on Apple) | An explicit level of tiles between the thread block and the thread | [G10](../../gpu/g10-matmul-ladder.md) |
| 10 | Double buffering | Loading the next tile while computing on the current one hides memory latency | [G10](../../gpu/g10-matmul-ladder.md) |
| 11 | Matrix units (opt-in) | Tensor cores on NVIDIA, SIMD-group matrix operations on Apple | [G11](../../gpu/g11-matrix-units.md) |

Rung 11 is separate because matrix units can change results. NVIDIA's first
tensor cores, for example, took FP16 inputs.[^tensor-cores] Vortex's
philosophy asks for explicit permission before any transformation that can
change observable results
([safety philosophy](../../philosophy.md#safety-philosophy)), so rung 11 is
reported apart from the others and only as an opt-in.

Three rules decide what counts:

- **Generated by Vortex.** A rung counts only when Vortex generated its
  kernel. Hand-written kernels are welcome for learning and as references,
  and they appear in the tables marked as hand-written.
- **One computation, many schedules.** Ideally every rung comes from the same
  Vortex matrix multiplication with only the schedule changed, which is the
  philosophy's second principle
  ([say what to calculate, then decide how to run it](../../philosophy.md#2-say-what-to-calculate-then-decide-how-to-run-it)).
  Where a rung needed a change to the source, the page says so.
- **Checks proven away, not dropped.** With fixed shapes the compiler can
  prove that every access in these kernels is in bounds, so the kernels need
  no runtime checks. A kernel whose checks cannot be proven is out of scope,
  because reporting a runtime error from inside a GPU kernel needs a design of
  its own.

Not in this study: fused kernels such as FlashAttention
([G12](../../gpu/g12-flashattention.md)), AMD GPUs, tile languages
([G13](../../gpu/g13-tile-languages.md)), more than one GPU per vendor, and
precisions other than FP32 outside rung 11.

## Method

The measurement protocol is on
[How Vortex performance is measured](../measuring.md), the test protocol is
on [How Vortex is tested](../testing.md), and chapter
[G14](../../gpu/g14-measuring-gpu-code.md) covers what is specific to GPUs.
This section adds only what is specific to this study.

### What is compared

For each rung on each GPU:

1. **Result** against the CPU reference: bit for bit where the floating-point
   settings and the order of additions for each element of C match the
   reference; otherwise the largest error, the reason for it, and the opt-in
   that allows it.
2. **Time:** the median and 95% confidence interval of the kernel's run time,
   and GFLOP/s computed from it.
3. **Fraction of the vendor library,** at the same shape and precision,
   measured in the same session.
4. **Fraction of a derived peak.** Peak FP32 throughput comes from a kernel of
   independent fused multiply-adds, or from a vendor figure with its citation.
   Device-memory bandwidth comes from a copy kernel. Together they draw the
   **roofline**, a chart that bounds attainable performance by peak
   arithmetic throughput and by bandwidth times arithmetic
   intensity.[^roofline]
5. **Counters:** one or two profiler counters per rung, chosen before the run,
   that should move if the rung's idea is right. On NVIDIA they come from
   Nsight Compute sections such as memory workload analysis and warp state
   statistics;[^ncu] on Apple, from Xcode's GPU counters.[^gpu-counters]

The matrices are square, FP32, and sized as a multiple of the largest tile,
plus one size that is not a multiple, to test how the kernels handle edges.

### Machines

- **Apple:** the owner's M4 Pro GPU. The setup table records its GPU core
  count and the macOS version.
- **NVIDIA:** one rented GPU, the same model for every rung. The setup table
  records the model, compute capability, driver and CUDA versions, and clock
  settings. Rented machines vary between sessions, so the vendor library runs
  again in every session and every ratio uses that session's numbers.

### What counts as success

1. **Correct at every rung.** Rungs 1 to 10 give results bit-for-bit equal to
   the CPU reference on both GPUs. Rung 11 stays within an error bound written
   down before the run, under an explicit opt-in.
2. **Generated, not hand-written.** Every rung claimed as compiler output was
   generated by Vortex.
3. **Explained.** Every rung has its counters, and they moved in the
   predicted direction. A rung whose counters did not move goes under "What
   did not work", even if it got faster.
4. **Reported in full.** Every rung has absolute GFLOP/s, the fraction of the
   vendor library and the fraction of derived peak. No target percentage is
   set in advance. For context only: the worklog this ladder follows ended at
   93.7% of cuBLAS, on an RTX A6000 with 4092 × 4092 FP32 matrices, in
   2022.[^boehm] That was different hardware and hand-written kernels, so it
   is not a target here.

Columns in both ladder tables:

- **Generated by Vortex:** yes, or "hand-written" for a reference kernel.
- **Median time and 95% CI:** kernel time only, at the shape in the setup
  table. Data transfer is excluded, and so is the run-time compilation of MSL
  source on Apple, which is reported separately.
- **GFLOP/s:** 2 × M × N × K divided by the median time.
- **% of MPS, % of cuBLAS:** this rung's GFLOP/s divided by the vendor
  library's, measured in the same session.
- **% of derived peak:** GFLOP/s divided by the peak in the roofline table.
- **Bitwise equal:** whether every element of C equals the CPU reference
  exactly.

## Threats to validity

- **Borrowed numbers.** Published ladders were measured on other GPUs at
  other sizes. None of their numbers appear here as results.
- **Timing GPU work.** A kernel launch returns before the kernel finishes, so
  the timer must wait for completion. On Apple the first launch also includes
  compiling MSL source,[^makelibrary] which is timed separately.
- **Profiling changes timing.** Timings come from runs without the profiler
  attached; counters come from profiled runs, which may run slower.
- **Vendor library settings.** The vendor library must run at the same
  precision, without reduced-precision fast paths, or the comparison favours
  it. The settings used are recorded.
- **Rented machines vary.** Drivers, clocks and temperature differ between
  sessions. The per-session baseline handles part of this, and the setup
  table records the rest.
- **What the Apple track can explain.** On Apple, the lowest level with public
  documentation is Metal Shading Language source,[^msl] so explanations rest
  on counters and source rather than on reading machine code.
- **Scope.** FP32, one family of shapes and one GPU per vendor. The results
  say nothing about other GPUs.
