# Case studies

<p class="page-intro">A case study is a short report on one piece of Vortex work that a reader can check without trusting the author: one question, one method, one result, and a link to every piece of evidence. This page explains the format, lists the ten planned studies with their status, gives the order in which to build them, and sets out the template they share.</p>

For an overview of the whole project and what exists in the repository today,
start at [Vortex for reviewers](../index.md).

## What a case study is

The rest of this site teaches. The [compiler guide](../../compiler/guide/index.md)
explains how to build Vortex, the books explain optimization, back ends, GPUs
and MLIR, and the [specification](../../specification/index.md) says what
Vortex programs mean. A **case study** does a different job. It reports what
was built and what happened when it was measured or tested, so that a reader
can decide whether to believe it.

Each case study has four parts.

- **One question.** A single question with a checkable answer, usually a
  number or a yes or no. "Is the compiler fast?" is not a question in this
  sense. "How close does the compiler's best strict matrix multiplication
  come to Apple's Accelerate library on one core?" is.
- **One method.** What is compared with what, on which machines, with which
  statistic, and what counts as success. The method is written before the
  first measurement, so the goal cannot move to meet the result.
- **One result.** The measured answer, including one that disappoints. A
  result that misses its target is still a result, and the page keeps it.
- **All evidence linked.** The commits that did the work, the tests that
  check it, the CI runs, the raw data, and one command that rebuilds the
  tables from a clean checkout.

The format exists to make checking fast. An engineer reading a case study
should find the claim, the number behind it, the command that produced the
number and the commit it came from in a few minutes.

All ten studies assume a working v0.1 compiler, except
[A5](upstream-contributions.md), which can start at any time.

## Two rules

**Empty means not measured.** Every results table on these pages starts empty
and stays empty until a measurement fills it. Nothing is estimated into a
measured column. When a model predicts a number, such as a throughput from a
static analyzer, it goes in a column labelled as a model, next to the
measured one and never in its place. This is the site holding itself to the
rule the [philosophy](../../philosophy.md#programmer-and-compiler-responsibilities)
sets for the compiler: never present an unverified estimate as a measured
result.

**The method comes first.** Each case study page exists, with its question,
method and success criteria, before the work starts. If the method changes
once results arrive, the page says what changed and why. Every page also
records the complete setup (hardware, software, flags and commit), which
Hoefler and Belli ask of any published performance result so that others can
repeat and interpret it.[^hb]

## Status and the evidence ledger

Each case study carries one status line near its top. The statuses match the
ones on [Vortex for reviewers](../index.md#how-claims-are-backed), and a status
changes only together with a link to its evidence.

| Status | Meaning |
| --- | --- |
| Not started | The page is a template. No work has been done, and every results table is empty. |
| In progress | Work has begun. The page links the first commit and fills a cell only when the evidence for it is in the repository. |
| Done | Every results table is filled from raw data in the repository, each success criterion has been checked (met or not), the reproduce command works from a clean checkout, and a passing CI run is linked. |
| Stopped | Work ended before Done. The page keeps what was measured and says why it stopped. |

The table in the next section doubles as the site's **evidence ledger**: a
list of what Vortex can demonstrate, each entry tied to a date and a commit. A
row changes only in the commit that adds the evidence it points to, so the
ledger never claims more than the code does.

records the real dates once work starts.

## The order to build them in

The order ranks the studies by how much checkable evidence each one produces
per week of work, and it respects what each needs from the others.

1. **A2, the measurement harness.** It is small, and every performance number
   after it depends on it. Building it first means no number on this site is
   older than a trustworthy way to take it.
2. **A1, the CPU ladder.** It continues directly from
   [stage 10](../../compiler/guide/stage-10-matrix-multiplication.md#why-speed-can-wait),
   whose naive matrix multiplication is the answer every faster version must
   reproduce, and it shows compiler skill and performance skill in one piece
   of work.
3. **A3, differential testing.** Once passes rewrite code, a silent
   miscompile is the largest risk. Random programs compared across execution
   paths guard every study after this one.
4. **A5, upstream contributions, started early and kept running.** A first
   small patch takes little effort, but review takes calendar time, so the
   record should grow alongside everything else.
5. **A4, the LLVM IR back end.** The most direct route to real LLVM
   experience, and a second path for A3 to compare against.
6. **A7, the MLIR lowering path.** It reuses A1's kernels and A3's
   comparisons, with MLIR's transformations in place of Vortex's own.
7. **A9, the cost model and autotuner.** It needs A1's passes to choose
   among and A2's harness to check its predictions.
8. **A8, the GPU ladder.** It repeats A1's method on a GPU, and its CUDA half
   needs access to NVIDIA hardware.
9. **A6, the native AArch64 back end.** The largest study.
10. **A10, the ML framework bridge.** It only makes sense once A1 or A8 has
    produced fast kernels worth calling.

The [back-end book](../../backend/index.md) builds a native back end soon
after v0.1, which moves A6 much earlier. That is a sound choice, especially
for anyone aiming at back-end teams, where instruction selection, register
allocation and scheduling are the daily work. For teams that work inside LLVM,
A4 and A5 together show more per week. Either way, A2 comes first.

### Why this order

The order follows what compiler, kernel and performance teams ask candidates
to show, taken from a reading of public job postings in September 2026 and
ranked here by how directly a stranger can verify each kind of evidence.

1. **Reviewed, merged work in a production compiler.** Other experts have
   already checked it, in public. This is [A5](upstream-contributions.md).
2. **Measured performance with a model behind it:** absolute numbers, a share
   of a derived peak, a comparison with a vendor library, and an explanation
   of the gap that remains. These are A1, A2, A8 and A9.
3. **A working, tested compiler that others can build and run.** This is
   Vortex itself, made trustworthy by A3 and extended by A4, A6 and A7. It
   carries the most weight for early-career roles.
4. **Presence in the compiler community:** meetings, forums, office hours and
   reviews of other people's patches. This is part of A5.
5. **Documentation.** It helps only as a fast route to the other four. A
   polished page about unfinished work is weak evidence, which is why every
   table on these pages starts empty.

## The shared template

Every case study page uses the same sections, in the same order.

| Section | What it holds |
| --- | --- |
| Title, intro, status | `# A<n>. <Title>`, a one- or two-sentence intro, and a status line with the planning size. |
| The question | The question in one sentence, and the claim the page will make when the work is done, with a blank for every number. |
| Why employers care | Which skills the study demonstrates and for which kinds of teams, in the author's own words. No quotations from job postings. |
| What to build | The work, each part linked to the chapter that teaches it, and what the study deliberately leaves out. |
| Method | What is compared with what, on which machines, the protocol (linked to [How Vortex performance is measured](../measuring.md) and [How Vortex is tested](../testing.md)), and the success criteria, written before the first run. |
| Setup | Hardware, operating system, compiler and library versions, flags, and the Vortex commit. |
| Results | Tables with every column defined. Absolute numbers first, then ratios to a named base. Variability shown. Empty until measured. |
| Analysis | Why each result came out as it did, backed by counters, IR or assembly excerpts. |
| What did not work | Attempts that failed, and the known limits. |
| Threats to validity | What could make the result wrong or misleading, and what was done about each threat. |
| Reproduce | One command that works from a clean checkout, the scripts it runs, and where the raw data lives. |
| What a reviewer should look at | The evidence: commits, tests, CI runs and raw data, each linked once it exists. |
| Sources | A footnote for every claim about the outside world. |

## Rules for filling in results

These rules apply to every results table. The
[measuring page](../measuring.md) gives the full protocol.

- Absolute numbers come before ratios, and every ratio names its base and
  gives the base's absolute value.[^hb]
- Every summary names its statistic, and every non-deterministic measurement
  shows its spread, as a confidence interval or the full distribution.[^hb]
- Every table names its machine, date and commit.
- Raw data lives in the repository, one row per sample, next to the script
  that produced the table.
- Model predictions sit in their own labelled columns.
- Negative results stay on the page.
